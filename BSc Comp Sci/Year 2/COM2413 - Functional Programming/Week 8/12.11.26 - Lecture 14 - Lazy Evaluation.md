
#### Lazy Evaluation
A lazy functional programming language *evaluates* the arguments of functions *only when necessary* and *only as far as necessary* to give a result. Haskell is lazy *by default*.

There are two important parts to this definition:

**Only when necessary**
Haskell *delays* performing computations until their result is actually needed.

Consider the following expression: `x = 1 + 1`. Since Haskell is lazy, it will delay the evaluation of `x` until the value of `x` is actually needed. Therefore, Haskell represents `x` as an *unevaluated computation*, called a **thunk**. This is what David Wakeling means when he says "evaluate the variable/argument".

Now, this might not seem impressive, but it gets really powerful when we introduce expensive computations. Given the following variables:
```Haskell
expensiveComputation = sum [1..10000000000000000]
result = 10
```
Since Haskell is lazy, `expensiveComputation` is represented as the computation `sum [1..10000000000000000]`, a thunk; i.e., Haskell doesn't actually calculate the summation. Now, since `expensiveComputation` is never used, it remains *unevaluated*, saving a huge amount of computational cost and speeding up the program dramatically.

**Only as far as necessary**
The is the more subtle part of the definition, but equally as important. Haskell doesn't need to evaluate every part of a data structure.

Consider the following expression: `x = (1+2,3+4)`. Since `x` represents a data structure, a tuple, Haskell will evaluate `x` to **Weak Head Normal Form (WHNF)**; it will *only evaluate the outer most structure*, revealing that `x` is a tuple, and leaving the expressions inside as thunks. The same principle applies to lists and other structures.

On the other end of the spectrum, we have *eager evaluation*, such programming languages include Java, C#, etc, which will evaluate a variable immediately, not matter if the result is used or not.


#### Producer-Consumer Behaviour
Lazy evaluation gives producer-consumer behaviour, effectively implemented using coroutines.

A **producer** is something that *generates data*, our generator.

A **consumer** is something that receives and *processes that data*, our selector.

In an eager evaluating language, the producer might generate all data before the consumer starts processing it. However, in a lazy programming language, Haskell, the producer generates one piece of data, the consumer processes it, then the producer generates the next piece of data, and so on.

A **coroutine** is a computation that can *suspend its execution* and *later resume* from where it left off.
