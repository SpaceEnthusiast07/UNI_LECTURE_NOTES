
#### Recap
**Race conditions**
When two threads try to access the same data at the same time, but don't know which should have access.

**Livelock**
When two threads spend too much time avoiding each other and not getting any useful work done.

**Deadlock**
When two threads need access to a recourse, but the other thread is holding it. It is a stalemate and no useful work gets done.


#### Atomicity
**Atomicity** is the idea that certain *operations must happen as one indivisible operation*, even if they aren't, to avoid lost updates. I.e., these *operations cannot be interrupted halfway through*. Before explaining, we need to define what fresh and stale data means.

**Fresh Data**
When threads are accessing data, we need to ensure it is **fresh**; ensuring the *data is up-to-date*.

**Stale Data**
When the *data is not up-to-date*, it is known as **stale data** - intuitive 😂.

An example of visibility in action is with the `++` increment operator. Below is some example code:
```Java
class Counter {
	private int c = 0;
	
	void increment() {
		c++;
	}
	
	int value() {
		return c;
	}
}

public class Main {
	public static void main(String[] args) throws Exception { 
		Counter counter = new Counter();
		
		// Uses a lambda expression; explained later on
		Thread t1 = new Thread(() -> { 
			for (int i = 0; i < 100000; i++) counter.increment(); 
		});
		
		Thread t2 = new Thread(() -> {
			for (int i = 0; i < 100000; i++) counter.increment();
		});
		
		t1.start(); t2.start();
		t1.join(); t2.join(); 
		System.out.println("Expected: 200000");
		System.out.println("Actual: " + counter.value());
	}
}

-- OUPUT 1 -----------------------------------------------------------------------
Expected: 200000
Actual: 180689

-- OUPUT 2 -----------------------------------------------------------------------
Expected: 200000
Actual: 124996
```

Firstly, lets understand the `join()` method, as we already understand `start()`.

When a thread, e.g. `ThreadA`, calls the `join()` method on, for example, `ThreadB`, specifically `ThreadB.join()`, `ThreadA` pauses its own execution and waits for `ThreadB` to complete. Once `ThreadB` has finished, `ThreadA` resumes its execution.

Applying this understanding to the program above; the main program, `Thread-Main`, calls the `join()` method on both `Thread1 (t1)` and `Thread2 (t2)`, meaning `Thread-Main` will wait until both `Thread1` and `Thread2` have finished before it resumes its execution.

Now, onto the main point of this example code: the differing outputs. This arises because whilst `Thread1` has read `c` and is performing the increment operation on `c`, `Thread2` is also reading `c`. This causes `Thread2` to read *stale data* (out-of-date data). So, once `Thread1` has finished and writes its update to `c`, it is immediately lost when `Thread2` writes its own update to `c`.

This is where **atomic variables** come in. These are imported objects that ensure operations performed on their respective primitive types are atomic or uninterruptable.

To access these atomic variables, you must import `java.util.concurrent.atomic`, which gives you access to atomic primitive types, such as `AtomicInteger`, `AtomicLong`, `AtomicBoolean`, etc.

These are objects so have functions used to manipulate the data, such as `get()`, `set()`, `incrementAndGet()`, `decrementAndGet()`, etc.

Use atomic variables when you only have *one variable you want to share between threads*.


#### Synchronisation
To solve the `c` counter example above, one way was to use atomic variables, but another is to use synchronisation.

**Synchronisation** ensures *only one thread can access a method of an object at one particular time*; this ensures the thread, and any subsequent thread, accesses fresh data within the method.

Think of synchronisation as *putting a variable in a room*, the *room being the method* used to access this variable (e.g. a getter). Once one *thread enters the room* (enters the method), *the door (method) is locked*, meaning this thread can *freely execute* the method; then, once it has finished, it leaves and another method can come in. This way, every time a thread enters the method, it can *access fresh data*.

However, synchronisation is more computationally expensive because the JVM must manage locks on methods and ensure locks are placed and freed correctly, which adds overhead.

Synchronisation is best used when you have *multiple operations you want to protect*.


#### Visibility
**Visibility** is concerned with *one thread seeing another's update*.

```java
class LoopMayNeverEnd {
    boolean done = false;
	
    void work() {
        while (!done) {
            // do work
        }
    }
	
    void stopWork() {
        done = true;
    }
}
```
In the example above, if `ThreadA` calls `work()`, and `ThreadB` calls `stopWork()`, `ThreadB` has now updated the variable `done` to `true`, meaning `ThreadA`'s loop should immediately stop; however, it doesn't. This is because `ThreadB` has updated its local cached version of `done`, meaning `ThreadA`'s local cached version of `done` is unchanged. This is where the `volatile` keyword comes in.


#### Volatile Variables
A **volatile** variable tells the JVM to *not allow local thread caching of the variable*, which means giving each thread its own local copy, but instead *forces all threads to access the shared copy*. This means that if any thread were to update the variable, all other threads could see the update.

>[!WARNING] `volatile` does NOT make things atomic.

Use `volatile` when you have a *flag that must be seen by all threads*.


#### Atomic, Visibility, and Synchronised Analogy
Imagine two people working on a whiteboard:

*Atomicity* would mean that one person cannot interrupt the other whilst they are doing something on the board.

*Visibility* would mean that when you look at the whiteboard, make sure it is the current, up-to-date version.

*Synchronisation* would mean that only one person can write something on the whiteboard at any single time.


#### Publishing and Escaping
**Publishing** refers to *making an object available outside its original scope*. This is done by providing a reference to this object to another program or part of a program.

You *must not publish* an object *unless you really have to*. If an object is *published by accident*, that object is said to have **escaped**.


#### Thread Confinement
**Thread confinement** refers to the idea that if *data doesn't need to be shared* between threads, then that data can be *confined to the single thread* that needs access. By confining data to a single thread, this automatically ensures thread safety.

If only a single thread ever accesses some data, that data is considered *confided*.

Thread confinement is an element of the program's design.


#### Lambda Expressions
Lambda expressions *introduce aspects of functional programming* into Java.

A **lambda expression** is a *block of code with optional arguments* that you can *pass between objects*; previously, you could only pass objects and primitives between objects.

Essentially, a lambda allows you to *pass in behaviour*/code into a method rather than just data.

The format of a lambda expression is: `(arguments) -> {body of code}`.

There are some extra notes that make sense:
 - You can have 0 or more arguments - with 0 you must have empty brackets
 - With a single argument, the brackets can be omitted
 - The argument type can be declared or inferred
 - The curly brackets can be omitted on the body with only one statement

Here is an example of lambda expressions in the wild:
```Java
@FunctionalInterface
interface Calculator {
    int calculate(int a, int b);
}

public class GFG {
    public static void main(String[] args) {
        Calculator add = (a, b) -> a + b;
        Calculator multiply = (a, b) -> a * b;
        Calculator subtract = (a, b) -> a - b;
		
        System.out.println("Addition: " + add.calculate(10, 5));
        System.out.println("Multiplication: " + multiply.calculate(10, 5));
        System.out.println("Subtraction: " + subtract.calculate(10, 5));
    }
}
```

You might have read everything about lambda expressions and still be confused; well, the reason is because lambda functions can only be provided to what are known as functional interfaces.

**Functional interfaces** are interfaces with *only one abstract method*; a method declaration with only a signature (return type, name, and parameters), but no body.

This is were *lambda expressions* come in; they *provide the abstract method's implementation*.

It is recommended, but not required, to provide the `@FunctionalInterface` annotation above the particular interface to enforce this rule at compile time.
