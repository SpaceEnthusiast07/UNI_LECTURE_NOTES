**Concept of Operations**
Details the *goals and objectives of the system*; the strategies, tactics, policies, and constraints affecting the system; and the process of initiating, developing, maintaining, and retiring the system.

**Requirement Analysis**
At this stage, you need to gather all the requirements of the system; ensuring they are clear, complete, consistent, and unambiguous. These are recorded in formal documentation.

**Design**
You will first design the **high level** aspects of the system, usually in the form of UML diagrams; ensuring you also detail the effects of this system on any external systems, and which need to be developed or upgraded.
You then have the **detailed design**, where you specify *how the system will be constructed*, such as what functions, classes, objects (quantity), and interfaces will be required.

**Advantages**
 - Highly structured - phases are completed one at a time and have a review at the end.
 - Works very well when all the requirements are understood.

**Disadvantages**
 - Once a project has progressed to the next phase, it can be difficult to go back; i.e., not suitable for projects with changing requirements.
 - Software is not written until late in the cycle.


#### Testing
Traditionally, we all treated testing as an extra step at the end of the development cycle. However, naturally, I do test as I go along; when you finishing writing a feature, you ensure the program compiles and runs as expected.

**Testing** ensures the system is working correctly and shouldn't be an after thought, an extra step; it should be completed *during and after the development*, which can actually save time overall. There are several levels of testing: Unit, Integration, System, and User Acceptance testing, which are described below.

**Unit Testing**
Unit Testing sounds scary, but it simply refers to what we already to, albeit without knowing the term. **Unit testing** simply means *testing individual units (blocks) of code in isolation*, to ensure they produce the correct output or effect.

**Integration Testing**
After performing unit testing, we know that all functions/methods work correctly in isolation, but **integration testing** ensures those methods *work correctly when integrated into the system*; i.e., do they work correctly together. Unexpected behaviour might arise once you integrate methods/modules, so integration testing is essential!

**System Testing**
Now that you know all units work correctly together, **system testing** involves testing the *system as a whole*, on a higher level, with test data and scenarios; some questions to ask include: does the system interface with external resources correctly, or is the overall performance and fluidity acceptable.

**User Acceptance Testing**
Testing the whole system with test data is all good and well, but you will never be 100% sure if your system works with real data, this is where **user acceptance testing** comes in. It is the process of testing the whole system with *real-world data and scenarios*; ensuring it meets the user's requirements, set out in the requirements analysis stage, and that the system is ready for use in the real world.


#### Testing Types
Alongside the different levels of testing, as described above, you also have different methods of testing, as described below:

**Static testing** involves testing the documentation and designs to ensure the system works. However, you also need to test the project itself, this is where **dynamic testing** is used; testing that actually involves *executing program code*.

**White box** testing involves knowing the internal code of the program so you can test many different paths through the code; however, this can lead to biases in the test cases that you design.

**Black box** testing involves treating the program as a black box, meaning you cannot see the internal code, resulting in test cases that the programmer may not have thought of; however, this may mean that the tests test a smaller number of paths through the code, so not a thorough.

**Grey box** testing is kind of a *middle ground*; you test the functionality (black box), but you also have access to a small amount of code or a non-user accessible database (semi white box).


#### Code Coverage
When performing unit testing (testing small specific units of code), it can be hard to ensure and keep track of what code has been tested. You have different types of coverage, detailed below:

*Method coverage* - has each method had a test written and performed on it?

*Statement coverage* - has each line of code been processes by at least one of your test suits?

*Decision coverage* - has every decision branch been tested (if-else statements)?

*Predicate coverage* - has every condition been tested; you might have an optimiser that doesn't test all statements in a compound conjunction statement (AND) if one is false?


#### EMMA & JaCoCo
**EMMA** is a *code coverage checker tool* developed for Java 5 and 6. **JaCoCo** has been developed to work with newer versions of Java.

You can invoke EMMA and JaCoCo from the command line, but most *popular IDEs integrate them*, and they can *colour code* each statement that has been covered.

These tools also provide the capability to define which level, method, statement, decision, or predicate, you wish to work at.
