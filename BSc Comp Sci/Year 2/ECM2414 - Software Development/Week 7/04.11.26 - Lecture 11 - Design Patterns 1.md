
#### Design Patterns
A **design pattern** is a *reusable approach* to solving a *recurring problem* in software design. 

It isn't necessarily a piece of code you copy and paste. Its more like a *blueprint* for how you might organise the classes and objects in your application.

A design pattern has been created by someone who has solved a similar problem to you before, with the aim of creating a *reusable structure* to aid the development of software in the future. Design patterns also improve a system's readability, maintenance, and scalability.

Hence, there are many different design patterns with the aim of solving different problems.

Remember back to A-Levels, when I used the *Model-View-ViewModel (MVVM)* program architecture (design pattern) in C# to make my project. Its aim is to decouple the GUI presentation logic (the View) from the business logic (the ViewModel) and the data itself (the Model). It is almost identical to the Model-View-Controller (MVC) architecture in Java.

What separates a good software dev from an excellent one is their understanding of core design patterns.

There are several categories of design patterns, each with the aim of solving a specific type of problem.
- *Creational* Patterns - Concerned with the creation of objects
- *Structural* Patterns - Concerned with how classes and objects are composed together
- *Behavioural* Patterns - Concerned with how classes and objects communicate with each other


#### Object-Oriented Principles
You might wonder how OO principles are linked to design patterns; well, OO principles are what underpin design patterns in the first place. Arguably, the following OO principles are more important than the design patterns themselves.

##### Principle 1: Encapsulate what varies
This means identifying the parts of your system that are likely to change (vary) and separate them from the parts that remain relatively stable.

##### Principle 2: Program to an interface, not an implementation
This allows parts of a system to work with an abstract reference type and not care about the specific instance type. Below is an example of this concept, once you see it, it makes sense:
```Java
Pizza pizza1 = new CheesePizza();
Pizza pizza2 = new VegenPizza();
```

This means that parts of your system can work with the `Pizza` interface, without knowing the specific pizza implementation it receives. This is polymorphism, and an important note is that the code depends on the behaviour promised by the interface, not the specific implementation of a particular class.

##### Principle 3: Favour composition over inheritance
Inheritance represents an *is-a* relationship, whereas composition represents a *has-a* relationship. For example, `CheesPizza` *is-a* `Pizza`, and `Pizza` *has-a* `Dough`.

Composition allows you to build objects using other objects, which is very useful when you want to add extra functionality or change the configuration without modifying the original class.


#### Factory Method Pattern
This is a creational pattern and it aims to solve: How can we create different types of objects without requiring the code that uses those objects to know how to construct them?

To help understand this pattern, we are going to use the pizza shop example from the Heads First Design Patterns book. Below is a simple example of this pizza shop:
```Java
public class PizzaShop {
	public Pizza orderPizza(String type) {
		Pizza pizza;
		
		if (type.equals("cheese")) {
			pizza = new CheesePizza(type);
		}
		else if (type.equals("vegetarian")) {
			pizza = new VegetarianPizza(type);
		}
		
		pizza.prepare();
		pizza.bake();
		pizza.cut();
		pizza.box();
		
		return pizza;
	}
}
```

Now, the problem arises when our pizza shop expands and offers more types of pizza; you must change the `orderPizza()` method, and this conditional becomes complex.

Most importantly, `PizzaShop` now needs to know how to create a pizza and how to process an order.

The solution is to use the factory method. The key idea is to separate out the logic for deciding which object to create from the logic that actually uses that object. Below is the revised `PizzaShop`, utilising the factory method.
```Java
public abstract class PizzaShop {
	// Just orders a pizza
	public Pizza orderPizza(String type) {
		Pizza pizza = createPizza();
		
		pizza.prepare();
		pizza.bake();
		pizza.cut();
		pizza.box();
		
		return pizza;
	}
	
	// Just creates a pizza
	protected abstract Pizza createPizza(String type);
}
```

Now, with this design, we can create different `PizzaShops` with different implementations of `createPizza()`, such as a `RomePizzaShop`, or a `NaplesPizzaShop`.

#### Abstract Factory Pattern
This is another creational pattern and aims to build a family/set of related objects. 

**The Idea**
You create a factory interface which states the factory methods required to create the set of related objects. Then, the implementing factory adds the necessary details of those factory methods for its specific combination of related objects.
