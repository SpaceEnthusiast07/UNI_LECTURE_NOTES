
#### Version Control
A **version control** system keeps a record of the *changes* made to files, which allows you to track the development history of a project and see who did what and when.

They allow teams of developers to work on a project simultaneously without overwriting each others work.

We have many systems to choose from; the main one being Git, but others include Mercurial, Concurrent Versions System (CVS), and Subversion (svn).

The main stream of changes, known as a branch, is called the main branch or trunk.

**Branching** allows you to work on a different version of the entire project that is completely independent of any other branches. They allow you to develop features in isolation and can be merged back into the main branch when complete.

**Merging** is the process of taking all the separate branch commits and bundling them up into one big commit, then added this new big commit to the main branch or trunk.

**Forking** is very similar to branching, but creates a new entire repo that is completely independent of the original.

**Locking** is the process of restricting access to files so that problems cannot occur when two people work on a file simultaneously. You have two types: strict - only one person can change a file at any one time; optimistic - any files can be edited, but need to be updated with main branch (repo) before committing to avoid merge conflicts.
 - Since the version control system is an algorithm, it doesn't understand the code, so cannot merge files with differing contents, as it doesn't know what to keep. This is where you must step in and manually merge the files.


#### Centralised vs Distributed Repos
A **repo**, or repository, is the *actual store for all the changes* you make to all files that are tracked.

With a **centralised** repo, you commit (save) your changes to a central repo, meaning *everyone sees your changes as soon as you commit*.

However, with a **distributed** repo, when you commit (save) your changes, they are first *stored in your local offline repo*. Then, when you want, you can *push* your changes *to the main repo*, usually located in the cloud (e.g. GitHub).

#### Version Numbers and Tags
By default, each file is given a version number that can be customised.

However, a version number isn't rememberable nor descriptive, therefore, we have version tags that can be placed on multiple files and provide a meaningful name or description for that specific version.


#### Good Practice
Repos aren't for just storing code, you can store ANYTHING.

However, there is a rule of thumb for what should be stored in a software dev project: anything that contributes to the understanding or ability to rebuild the project must be included in the version control tracking; however, anything that is automatically generated (such as Javadoc or compiled code/binary files) must not be as this can bloat the repo and make it harder to manage.
