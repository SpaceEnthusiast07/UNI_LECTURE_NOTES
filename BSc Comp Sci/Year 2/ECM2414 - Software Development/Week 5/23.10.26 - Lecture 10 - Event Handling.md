
#### Programming Paradigms
A paradigm is a fundamental method or structure used to build something.

Therefore, we can apply this to programming and say that a **programming paradigm** is a *fundamental* way to *building the structure* and flow of a program.


#### Why use Event Handling?
At some point during a program, it will have to wait for something to happen. In this scenario, you have two options: *poll for the event* or implement *events listeners* for those events.

**Polling**
This solution involves the program repeatedly checking to see if the event occurs. Naturally, this wastes resources if the event is not frequent as the program is not doing any useful work whilst checking for the event.
However, polling is simple to implement as all it requires is a loop that checks a flag, for instance.

**Event-driven Programming**
This solution involves a contract between the program and the Operating System; when an event occurs, it interrupts the OS, which in turn notifies the program of the event, via a specific method call.
Naturally, this solution is more complex to implement, but makes far more effective use of resources.

Event-driven programming is fundamental when implementing GUIs; they have numerous elements that the user can interact with, so your program must be able to *react* to these events, rather than simply waiting for them to happen.

However, events and listeners are not restricted to GUIs, they can be used for anything.


#### The Delegation Model
Event-driven programming is implemented in Java using the **delegation model**. If an object wants to receive notifications of an event, it must register an event listener specific to that event.

**Source**
This is the object that *triggers an event*; such events include an internal state change of the object, e.g. the click of a button. Source objects must register event listeners in order for listeners to be notified.

**Listener**
This is the object that is *notified of an event occurring*; it is the class you write that must *implement* an event *listener interface* to be notified. Since you are implementing the listener interface, you must *implement* certain *methods* that deal with certain types of events.

**Event**
The is the object that contains data about the event; such as the class name of the object that triggered the event, what specific type of event occurred, and other useful information.


#### Events and Listeners
Different types of *events* are *grouped* to be more specific to which source object triggers them. For instance, all events triggers by buttons are categorised as `ActionEvent` and by keys on the keyboard are categorised into `KeyEvent`.

Regarding event listeners, and event objects, they are named `<event_category_name>Event` and `<event_category_name>Listener`, by convention.

Therefore, a button will trigger an `ActionEvent` which notifies an `ActionListener`.

Regarding `KeyEvent` and `KeyLinstener`, the implementing class must define:
 - `keyPressed(KeyEvent e)` - called when a key is pressed down, plus the raw value of the key.
 - `keyReleased(KeyEvent e)` - called when a key is released, plus the raw value of the key.
 - `keyTyped(KeyEvent e)` - similar to the other methods, but the value of the key is the one that is a result of multiple key presses; i.e., can recognise the different between `Shift + g`, which results in `G`, and `g`, which simply results in `g`.


#### Custom Sources
The event-driven framework is flexible, so allows you to create your own source objects. However, they must define certain methods for adding event listeners, for instance the `addActionLister()` method.
