
#### Networking Recap
Communication between two machines follows a strict hierarchical approach, known as the TCP/IP protocol stack, which breaks the steps down used for communication into layers:
 - Application - HTTP, FTP, Telnet, etc
 - Transport - TCP, UDP
 - Network - IP
 - Link - Device drivers, MAC, etc


#### Networking in Java
Since our Java programs are applications, we will be operating in the *application layer* of the TCP/IP stack.

The `java.net` API is used for networking in Java applications.

When setting up networking in Java, we need to specify which transport layer protocol to use, TCP or UDP.


#### Transmission Control Protocol (TCP)
**TCP** is a *connection-based* protocol, meaning before the transmission of data, a link between the sender and recipient is established to ensure the recipient is on and ready to receive data, which *guarantees delivery* of data due to the recipient sending *acknowledgments*.

TCP is an *end-to-end communication* protocol, meaning it utilises the IP address and port number of the sending and receiving applications, rather than the link layer which governs routing between intermediate devices (hops between routers).

One key property of TCP is that the *order of data received is guaranteed* because its uses sequence numbers on packets of data, which are reassembled on arrival.

Another key property is that TCP will retransmit data in the event data is lost or an acknowledgement from the recipient hasn't arrived within a certain amount of time.


#### User Datagram Protocol (UDP)
**UDP** is a *connectionless* protocol, meaning it will send the data packets (datagrams) to the recipient *without acknowledgement* and even if the recipient is offline; hence, the *order of data is not guaranteed* and the sender will never know if the data reached its destination.

Therefore, UDP is *significantly faster* as it doesn't have any error checking, reordering, or acknowledgment to perform, and because there is no acknowledgement, *missing data is never retransmitted*.

Now, for many applications, this protocol is the opposite of we want. However, there are many applications that rely on UDP for fast transmission. Such applications include video streaming services and online games, where missing or mis-ordered data isn't a problem as the next frame is going to be shown very soon.


#### Ports
**Ports** are *purely logical* constructs used by the OS to *route incoming data to the application* expecting it.

Without ports, the only information a data packet would contain is the IP address of the destination computer, and the MAC address, of course. But, once the OS receives the packet, it won't know which app to send it to.

Port numbers *consist of 16 bits*, so there are $2^{16} - 1 = 65,535$ port numbers to choose from. The first `0-1023` are known as *system ports* and reserved by the OS for core tasks such as `22 - SSH`, `53 - DNS`, `80 - HTTP`, and `443 - HTTPS`. Then, `1024-49151`, known as *registered ports*, are ports registered by applications for their specific use, such as `3306 - MySQL`. The rest, `49152-65535`, are dynamic/temporary ports.


#### Sockets
So, this is where your understanding of what a socket was, was wrong!

A **socket** is the *endpoint* in the communication over a network. Your *application reads and writes data to this socket*; your application isn't the endpoint.

Now this does explain some questions that were brewing in my head. I was wondering how the OS passes the transmitted data to the respective application. The answer is quite simple. The *socket is like a buffer* (area of memory) in main memory (or at least that is a sub part of it) that the OS and your application read and write data to. It is the medium that allows communication over networks.

You previously thought that a socket was the *concatenation of the IP address and port number*, for instance `127.0.0.1:5000`. In fact, this is known as the **socket address**.

Once an application creates a socket, it registers it with the OS. The OS then *binds* that socket to a specific port number (from the *ephemeral port number range*), which, combined with the host computer's IP address, is the *socket address*.


#### Implementing TCP Sockets in Java
A socket on the client's side is represented by the `Socket` object from the `java.net` library. `Socket` represents an *actual TCP connection* that can send and receive data.

```Java
Socket socket = new Socket("localhost", 5000);
```
The above Java statement is used to create a new TCP connection. You must specify the destination IP address, `localhost` (keyword for `127.0.0.1`, the loopback IP address), and the destination port, `5000` in this case. We use `localhost` in this example to represent our own computer as our custom server is running on the same computer.

This simple one liner performs a lot of operations behind the scenes, namely:
 - Asking the OS to establish a TCP connection to `localhost:5000`.
 - The OS then assigns the client a local ephemeral port, e.g. `63404`.
 - A TCP connection is established using the 3-way hand shake.
 - The server, if online, receives this connection request and sets up its own socket.

Now, this is key, Java uses the `ServerSocket` object which *listens for TCP connection requests*, it does not represent the connection itself.
```Java
ServerSocket serverSocket = new ServerSocket(5000);
```
This tells the OS that this application, nicknamed server, wants to listen for TCP connection requests on port `5000`.

The server accepts a connection request by using the `accept()` method of the `ServerSocket` object, which waits until a client connects. It returns a new `Socket` object which represents the new TCP connection.
```Java
Socket newClientSocket = serverSocket.accept();
```

Now, as you may have thought, multiple clients are able to communicate with a server on the same port in the real world, just look at web servers, they constantly set up new connections on the same port. The key is that the `Socket` object contains both the source and destination IP address and port number, meaning the destination socket address (`IP:Port`) can be the same, but the source socket address can differ, allowing the server to distinguish between different TCP connections.

Just a new term, the destination socket address (`IP:Port`) is known as the remote socket/endpoint address.


#### Putting this all together in a Java Program
Below is a basic workflow to set up a new TCP connection:
1. Open a socket
2. Open an input and output stream for the socket
3. Read from and write to the streams
4. Close the streams then the socket

First, lets build a simple example, one in which the client sends a message to the server, and the server simply responds with the same message.

```Java
\\\\ Server.java ////
import java.io.*;
import java.net.*;
import java.nio.charset.StandardCharsets;

public class Server {
	public static void main(String[] args) {
		// Set up a new TCP connection listener on port 5000
        try (ServerSocket server = new ServerSocket(5000)) {
            // Ouptut successful TCP connection
            System.out.printf("LOG: Server listening on port %d\n", server.getLocalPort());

            // Wait for a new TCP Connection request
            // Program waits here until a new connection request arrives
            try (Socket client = server.accept()) {
                // Ouptut successful TCP connection
                System.out.printf("LOG: Client connected on port %d from remote address %s\n", 
                    client.getLocalPort(), client.getRemoteSocketAddress());
                
                // Initialise the input stream - receive data
                BufferedReader in = new BufferedReader(
                    new InputStreamReader(client.getInputStream(), StandardCharsets.UTF_8)
                );

                // Initialise the output stream - send data
                PrintWriter out = new PrintWriter(
                    new OutputStreamWriter(client.getOutputStream(), StandardCharsets.UTF_8), true
                );

                // Read the received message
                String message = in.readLine();

                // Log the received message
                System.out.printf("LOG: Received \"%s\"\n", message);

                // Echo the message back to the client
                out.printf("Echo: %s\n", message);
            } catch (IOException e) {
                System.out.println("ERROR: Couldn't create new client Socket.");
            }
        } catch (IOException e) {
            System.out.println("ERROR: Couldn't create new ServerSocket.");
        }
	}
}
```

```Java
\\\\ Client.java ////
import java.io.*;
import java.net.*;
import java.nio.charset.StandardCharsets;

public class Client {
	public static void main(String[] args) {
        // Create a new TCP connection with remote socket address "localhost:5000"
		try (Socket server = new Socket("localhost", 5000)) {
                // Ouptut successful TCP connection
                System.out.printf("LOG: Successfully connected to server with socket address %s\n", server.getRemoteSocketAddress());
                
                // Initialise the input stream - receive data
                BufferedReader in = new BufferedReader(
                    new InputStreamReader(server.getInputStream(), StandardCharsets.UTF_8)
                );

                // Initialise the output stream - send data
                PrintWriter out = new PrintWriter(
                    new OutputStreamWriter(server.getOutputStream(), StandardCharsets.UTF_8), true
                );

                // Send a message to the server
                String message = "Hello server and world of networking!";
                out.println(message);

                // Log sent message
                System.out.printf("LOG: Sent \"%s\" to server at address %s\n", message, server.getRemoteSocketAddress());

                // Receive the server's response
                String response = in.readLine();

                // Log the received message
                System.out.printf("LOG: Server replied with \"%s\"\n", response);
            } catch (IOException e) {
                System.out.println("ERROR: Couldn't connect to server.");
            }
	}
}
```

You might wonder what the `true` is doing in both the client's and server's output streams. This means that automatic flushing is enabled, meaning when ever data is written into the buffer, the buffer is flushed; i.e., the data is sent along the output stream and deleted from the buffer, ready for the next piece of data to send.
