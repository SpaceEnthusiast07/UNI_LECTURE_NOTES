
#### What is Concurrency?
**Concurrency** is about *structuring your program* in such as way that it *can be broken down into smaller processes (threads)* that can *either be run sequentially or in parallel* without affecting the final outcome.

The famous computer scientist Rob Pike puts it: "*Concurrency is about structure, parallelism is about execution*".

The job of the *compiler* is to *determine* whether the program's threads are *run sequentially or in parallel*. The *Operating System* then *determines* whether these threads will run on the *same core or across multiple cores*.

**Sequential processing** is where each task (thread or process) is fully completed before moving onto the next task (thread or process).

**Parallel processing** is where two or more tasks (threads or processes) are executed simultaneously, either on the same core (using round robin and time slicing) or across multiple cores (true parallelism).

As I alluded to above, if the compiler decides to run the threads in parallel, but the OS decides to run the threads on the same core or the computer has a single core processor, then the OS will use time slicing and round robin to rapidly switch between the threads to give the appearance that they are running in parallel. But, as we know, to achieve true parallelism, multiple cores are required.

#### What are Threads?
**Threads** are smaller, lightweight *baby processes* within a bigger main process (program), with the *ability to be executed sequentially or in parallel*.

You might wonder why we go to the extent of setting up threads when we can simply have separate programs. Well, the reason is because when we use threads, each thread has its own local memory space as well as access to a shared pool of memory between all threads and the main process. This allows easy sharing of data between threads without the head aches of memory management security.

To actually implement threads in Java, you can either extend the `Thread` class or implement the `Runnable` interface. However, because Java only lets you inherit from one class, if you inherit the `Thread` class, you now cannot extend any other class, making the interface method more desirable in most scenarios. Anyway, below is the format  of both methods:

```Java
// Extend method:
public class HelloThread extends Thread {
	public void run() {
		System.out.println("Hello from inside a thread.");
	}
	
	public static void main(String[] args) {
		HelloThread myThread = new HelloThread();
		myThread.start();
	}
}
```

```Java
// Runnable method:
public class HelloRunnable implements Runnable {
	public void run() {
		System.out.println("Hello from inside a thread.");
	}
	
	public static void main(String[] args) {
		Thread myThread = new Thread(new HelloRunnable());
		myThread.start();
	}
}
```

From these two examples, you can see that the `Runnable` method requires a tiny bit more set up, other than take, the `Runnable` method provided more advantages than the `Extends` method.

You might wonder why we are calling `start()` instead of `run()`. Well, calling `run()` is a regular method call and doesn't create a new thread; however, calling `start()` creates a new thread and then calls `run()`.

The thread naturally dies once the `run()` function has finished. In order to kill a thread before that, it must be interrupted.


#### What is Multi-Threading?
As you might have guessed from the name, **multi-threading** is where *a process creates multiple threads that can be run concurrently*.

As mentioned above, these threads can be run in parallel, either using time slicing on a single core or truly parallel on multiple cores.

With the introduction of multi-threading brings new problems to consider, namely **nondeterminism**. It sounds scary but simply means that because threads can run in parallel, one might finish before the other or the other way round, meaning you will *never truly be able to predict the output of the program*.

With the advent of nondeterminism arises the term **liveness**. You might be thinking how does this link to a computer and multi-threading. Well, previous to multi-threading, we have always been concerned with the safety of our code - ensuring it performs correctly. But now, we have to also think about liveness - *ensuring* our code performs correctly in time, meaning *that operations are performed in the correct order*.


#### What is Multi-Tasking?
Now, this you should already know and, if not, should have already worked out, **multi-tasking** is where the *OS manages how multiple main processes (applications) are processed* (such as a browser and email editor).

As with multi-threading, the OS can either use time slicing to make the appearance that each application is running in parallel or truly in parallel on multiple cores.


#### Race Conditions
A **race condition** occurs when *two threads try to modify the same data*, but the unpredictable executing order of the threads *results in an incorrect final result*.

Essentially, the final outcome of a program depends on the unpredictable order of thread execution.


#### Synchronisation
This is where synchronisation comes in. The aim of **synchronisation** is to *solve race conditions*.

When you use the `synchronized` keyword in a method declaration, whenever a thread calls a `synchronized` method, the execution of all other threads, that are trying to access other `synchronized` methods within the same object, are paused.

You can also simply synchronise a set of statements rather than a whole method using the below syntax:
```Java
public void aMethod() {
	// Regular statements
	synchronised (this) {
		// All statements in here are synchronised
	}
	//More regular statements
}
```


#### Atomic Actions
**Atomic actions** are *operations that cannot be stopped in the middle of their execution*; they either happen or they don't.

The read and write operations for all primitive data types in Java are atomic actions, except for floating point numbers.

To force atomic actions upon a variable, you can use the `volatile` keyword.
