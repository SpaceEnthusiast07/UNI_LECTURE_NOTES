
#### Mock Objects
When we want to test methods of a specific object, it may be difficult when it relies upon other complex objects to function. This is where mock objects come in.

**Mock objects** are *placeholder objects* that are predictable and allow you to test the method another another object.

We use mock objects when the real object is:
 - non deterministic
 - difficult to set up
 - some behaviour is hard to trigger
 - slow
 - uses a GUI or the CLI
 - doesn't exist yet

**Implementing mock objects**
We describe the behaviour of the production object in an interface, then implement that interface in the production code. You can then implement a mock object for the unit tests.


#### Test Suits
Up until this point, we have been writing test classes that are only concerned with testing a single class. **Test suits** allow us to *group together tests* to run as a *single batch*.

To write a test suit, you simply write unit tests as you would normally; i.e., on a per class basis, then you can give each test a category using the `@Category` test class/method annotation.

Using categories allows the main test suit class to run specific subsets (categories) of tests for each class. Such as just running basic fast tests or an extensive batch of all tests.


#### Test Driven Development
The whole idea boils down to:
 - Write feature
 - Test basics of feature
	 - If fail, improve feature
	 - If succeed, write more extensive tests
 - If extensive tests succeed, write more features
 - If fail, improve feature
 - Then, repeat.

Obviously, this is impossible to do if you haven't designed your project to accommodate unit tests and the test-driven-development methodology.


#### Invariants
Sounds scary, but **invariants of a class** are *properties* of that class that *must not change unless under the right conditions*.
