
#### Recap of Unit Testing
In programming, a **unit** refers to a *small, specific block of code*; i.e., small methods.

Hence, **unit testing** refers to the process of *testing individual methods in isolation* to ensure they work as intended.

It is *often impossible* or at least very difficult *to prove* that a method works as intended; the *best we can do is test enough possibilities* that we are satisfied with the outcome.


#### Right-BICEP
This is an acronym that is used to ensure you have tested the code as much as you can.
****
**Right** - are the boundary conditions correct/*right*?

**B** - are all *boundary conditions* correct?

**I** - can you check the *inverse* relationship?

**C** - can you *cross-check* the results using some other means?

**E** - can you force *error conditions* to occur?

**P** - are the *performance characteristic* within bounds/acceptable?
****


#### ATRIP
Now that you have asked all the questions in the Right-BICEP, you now need to ensure ATRIP
****
**Automatic** - should have little active input from a human.

**Thorough** - should test many aspects of functionality.

**Repeatable** - should produce the same results each time.

**Independent** - of other tests and the environment.

**Professional** - code is written and documented to the same standard as the actual product code.
****


#### Testing the Test
When a test reveals a bug in the code, try to improve the test to test for this extra bug.

During testing, *intentionally add bugs* to the code to *ensure the tests react as expected*.


#### JUnit
There are 3 main versions of JUnit are 4 through 6. We focus on JUnit 4 in this module.

During testing, you have *class pairs*: one class is the *product class* and the other is the *testing class*. The testing class should have the same name as the product class, but this the word "Test" on the end, and collects all tests that test the specific product class.

This convention extends to the testing methods; a *testing method should start with the word "test"*, but doesn't have to for JUnit to work; however, all testing methods should have the `@Test` *method annotation* to tell JUnit that this is a testing method.

General test set up:
 - Set up all properties required for the test to actually work, including the input for the method to test.
 - Call the method to be tested, with the required arguments.
 - Use `assertions` to ensure the method/object responds as expected.
 - Clean up after itself, ensuring the next test can run without an error caused by the previous test.

You can also define helper tests which either run before or after each test. They use the `@BeforeEach` and `@AfterEach` annotations respectively. You can also specify methods that run `@BeforeAll` and `@AfterAll` tests.

`@DisplayName` can be used to give each test a custom descriptive name.


#### JUnit Assertions
**Assertions** are using within unit tests to *check the outcome of a method*. They typically check for thrown exceptions; ensuring the tested method throws the correct exception given a certain input. Some commons ones are:

`asserTrue(String msg, boolean condition)` - if a `condition` is not `true`, then the `msg` is outputted.

Typically, a single unit test will have multiple assertions, but if an earlier one fails, the test stops and all subsequent assertions will not be checked.


#### JUnit Imports
You must import all these in each test class for JUnit to work.
```Java
import org.junit.BeforeClass; // for @BeforeClass
import org.junit.Before; // for @BeforeEach and @BeforeAll
import org.junit.Test; // for @Test
import org.junit.After; // for @AfterEach and @AfterAll
import org.junit.AfterClass; // for @AfterClass
import static org.junit.Assert.*; // for assertTrue(), etc.
```

You simply use `javac` and `java` to compile and run your JUnit testing classes, as well as passing in the JUnit core running with `-cp`.
