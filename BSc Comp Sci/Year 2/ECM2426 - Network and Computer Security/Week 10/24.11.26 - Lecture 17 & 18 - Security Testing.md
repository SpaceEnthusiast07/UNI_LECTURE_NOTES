
#### Security Testing
**Security testing** is a *systematic process* for checking whether software *meets its security requirements* and for *discovering vulnerabilities* that attackers could exploit.

There is an important distinction here, security testing is effectively a *bug-finding activity*, it isn't a mathematical proof of security.

As we have talked about in previous lectures, security needs to be implemented throughout the software development lifecycle, not just at the end! Therefore, we need to be security testing from an early stage and frequently.


#### Vulnerability Reporting
As established above, *no tool can reveal all vulnerabilities* in a system, and *all tools make trade-offs* which lead to false positives and false negatives.

This raises a *significant dilemma*: report all vulnerabilities, which results in amazing coverage, but leads to a higher chance of a false positives, annoying developers, which can lead to them ignoring critical issues later on; or, report only the high-confidence vulnerabilities, reducing false positives, but introducing false negatives, where critical vulnerabilities are missed.

#### Static Code Analysis
**Static code analysis** involves *inspecting the source code*, or some other representation of the system, such as UML, to ensure the system *functions as required* and *is maintainable*. The key part is static, the analysis takes place without running the system.

**Type Checking**
This involves ensuring the data type of the input to a program or function is correct before proceeding. For example, in Python we have tools such as `Mypy` and `Pylance/Pyright` which check whether the appropriate measures are in place to deal with incorrect types.

**Code Quality - aka Linting**
Linting is the process of ensuring your code is maintainable and conforms to the conventions of the programming language used. For example, in Python, function names should use snake_case, and unused imports, variables, and functions should be removed.

**Code Comprehension**
Documenting which modules depend on which other modules, and updating or changing modules when a security vulnerability is identified in that module. You also need to have a plan in place for when one module is updated and how that effects other modules.

#### Static Application Security Testing
**Static Application Security Testing (SAST)** involves *automatically* analysing the *source code*, or some other representation of the system, to *identify* potential *security vulnerabilities* before executing the application.

The key difference between SAST and manual code review is that SAST is automatic and performed using a tool such as `bandit` for Python, which we used in question 7 of the coursework.

Since these tools *don't understand* the code, they must *use rules and patterns* to identify potentially unsafe code; hence, they will not find all vulnerabilities, and will miss classify some vulnerabilities.

**General workflow of a SAST tool:**
 1. Input some representation of the system, e.g. the source code.
 2. Parse and model the representation of the system.
 3. Use rules and patterns to identify any potential vulnerabilities.
 4. Report the findings and provide the location, rule used, and confidence level.
 5. Let a human review the vulnerability to assess whether it is real or sever enough to deal with.

**Rule-based SAST**
This part of a SAST tool uses *predefined rules*, which could include certain modules or functions marked as insecure, meaning the presence of such module or function is a potential security vulnerability; hence, should be reported.

**Taint Analysis**
Can untrusted (tainted) data reach a sensitive operation, which can lead to malicious operations within the *sink*, the object that is affected. The main example is SQL injection. In this case, *parametrised queries* should be used, they treat the input as raw data rather than a command.

**Control Flow Limitation**
The control flow set up may mean tainted (untrusted) data may never reach a sensitive operation, but a SAST tool may or may not identify this vulnerability.

**Business Logic Limitation**
Generic SAST tools cannot infer business specific rules; therefore, you must customise the SAST tools you use to maximise the chance of revealing a vulnerability.

#### Dynamic Security Testing
**Dynamic Security Testing** is all about identifying vulnerabilities in a system by exploring it during runtime. The two types are penetration testing (manual) and DAST (automatic).


#### Dynamic Application Security Testing
**Dynamic Application Security Testing (DAST)** is the process of *automatically* identifying vulnerabilities in a system by analysing the system's behaviour during runtime.

Below are the general steps involved in a DAST model:
1. *Discover Attack Surface* - Identify URLs, APIs, parameters, authentication states, etc.
2. *Establish a baseline* - Understand the normal requests and responses so the tool has something to compare the tests to.
3. *Test* - Make a change, e.g. in an input, header, method or state.
4. *Observe* - Observe the response, the status, headers, body, timing, and side effects.
5. *Review* - Compare to baseline to determine if a potential vulnerability has been identified, if so, report with a classification, evidence, and confidence level.
