
#### Why Cryptography is not enough
Cryptography is absolutely necessary, but the software can still fail if the surrounding implementation is insecure.

**Over-permissive access** refers to giving regular users the access rights of users higher up than them; e.g., giving a regular user admin privileges for something.

**Zero-day vulnerabilities** are security vulnerabilities that no one knows about, so they have *zero days to fix them*.

Software is hard to implement securely due to immense codebases with millions of lines of code. This is a logical and some what obvious idea, but it is worth noting. A good example of a large codebase is the Linux kernel. In the initial release, in 1991, the kernel contained 170,000 lines of code, but fast forward to version 6.6 in 2025, it now has over 37 million lines. 

The co-founder of Stack Overflow, Jeff Atwood, famously said in 2007 that "the best code is no code at all". Now, he didn't mean write no code, but only write code that is absolutely needed and keep it simple, readable, and maintainable.


#### Some Security Definitions
A defect/**bug**/fault is a problem introduced in the requirements, design, implementation, or configuration of a system.

A **security weakness** is a type or class of security vulnerabilities that could go wrong, such as an SQL injection.

A **security vulnerability** is a specific instance of a weakness in a particular system.

A vulnerability may be exploited or triggered by a threat event, potentially causing security impact (a loss of confidentiality, integrity, or availability).


#### CVE, CWE, CVSS
**Common Vulnerabilities and Exposure (CVE)**
This is a public database of all reported security vulnerabilities. Each has a code similar to this one: `CVE-2025-61882`.

**Common Weakness Enumeration (CWE)**
Linking back to the previous definitions, a vulnerability is a specific instance of a weakness. Therefore, a CVE will be classified as an instance of a CWE, an instance of a weakness class.

**Common Vulnerability Scoring System (CVSS)**
Each CVE, or vulnerability, is given a severity score between 0 and 10, 10 being "CRITICAL".


#### Detecting Security Vulnerabilities
In a traditional software development lifecycle, for example, one that includes the stages requirements, design, implementation, and testing. A security vulnerability may be introduced in an earlier stage, but only detected during the final testing stage. This results in a costly fix.

The time between the introduction of the vulnerability to when it is detected is known as the detection delay.

The obvious, but important and difficult, solution is to *integrate security methodologies throughout the lifecycle*, so the system is built from the ground up to incorporate security measures.

**Security Requirements**
Part of the requirement analysis, the second stage in the cycle above, is to analyse the security requirements of the system.
A good requirement is specific, testable, tied to a threat, implemented by a control, and verifiable after a change.
A bad example is "the system must be secure", a better one is "Users must only access their own orders", but a really good requirement is "Every order retrieval must verify ownership on the server before returning order data".


#### Secure Design Principles
You must design security into the system, before the implementation.

**Least Privileges**
Give users the least amount of permissions. This limits the damage caused by a compromise.

**Complete mediation**
Every access to a protected object or operation must be authorised; e.g., does the requesting user have the right permissions.

**Secure by default**
The system is configured to be as secure as possible by default, but the user can configure otherwise, such as removing the use for a password.

**Defence in depth**
Instead of using one layer of protection, use multiple. This reduces the impact if one layer fails.

**Minimise attack surface**
The attack surface of a system is the number of possible points of failure i.e., a place where an attacker can attack the system from.
