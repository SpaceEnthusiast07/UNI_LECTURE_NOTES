
In the exam, they will give you a piece of code and ask you to identify any security vulnerabilities in that code. The programming language in the exam is most likely Python, but it shouldn't be too much of a problem if it isn't.


#### OWASP
Link: https://top10.owasp.org/2025/

Practice attacking vulnerable web applications on OWASP: https://owasp.org/projects/vulnerable-web-applications-directory & https://vwad.owasp.org/.


#### A01: Broken Access Control
Def: An actor can act outside their intended permissions.

Key Points:
 - Authorise on the server - Always check protected actions on the server, not the client side.
 - Deny by default - Only grant permissions that are explicitly required.
 - Scope data access - Limit read and write access to records the actor is allowed to access.


#### A02: Security Misconfiguration
Def: Security-related settings are unsafe, incomplete, inconsistent, or left at default/development values.

Key Points:
 - Make production safe by default - Disable debug and insecure compatibility settings
 - Keep the platform minimal - 
 - Set security attributes explicitly - 
 - Trust the configuration source - 


#### A03: Software Supply Chain Failures
Def: The software you deliver inherits risks from components, build tools, and repositories that you depend on.

Key Points:
 - Know the dependency tree - 
 - Choose maintainable components - 
 - Act on relevant advisories - 
 - Protect the build path - 


#### A04: Cryptographic Failures
Def: Sensitive data or credentials are unprotected, or cryptography is used with weak algorithms, randomness, keys, or protocols.

Key Points:
 - Use dedicated password hashing - 
 - Use cryptographic randomness - 
 - Use established cryptography - 
 - Protect keys separately - 


#### A05: Injection
Def: Untrusted data is interpreted as commands, queries, or executable content by another component.

Examples: SQL injection or Cross-Site-Scripting (XSS).

Key Points:
 - Parameterised queries - 
 - Use safe APIs - 
 - Encode for the output context - 
 - Validate business input - 


#### A06: Secure Design
Def: A required security control or business rule was never designed, so even correctly written code can remain unsafe.

Key Points
 - Keep security critical state on the server - 
 - Model allowed states - 
 - Design for misuse as well as normal use - 
 - Threat model critical flows - 


#### A07: Authentication Failures
Def: Allowing an attacker to be treated as another user or keep using authentication state that should no longer be trusted.

Key Points:
 - Use trusted authentication components
 - Resist automated guessing
 - Harden account recovery
 - Protect session state


#### A08: Software or Data Integrity Failures
Def: Code or data crosses a trust boundary and is treated as trustworthy without verifying its integrity.

Key Points:
 - Do not deserialise untrusted objects
 - Verify updates
 - Control trusted sources
 - Limit dynamic code loading


#### A09: Security Logging and Alerting Failures
Def: Security-related activity is not captured or acted on well enough, or the logging exposes sensitive information.

Key Points:
 - Log security-related events
 - Never log secrets
 - Make logs usable and protected
 - Turn important patterns into action


#### A10: Mishandling of Exceptional Conditions
Def: Errors, unusual states, or resource problems are ignored, exposed, or handled in a way that weakens security.

Key Points:
 - Handle expected failures
 - Fail securely
 - Separate user and diagnostic errors
 - Bound resources and clean up
