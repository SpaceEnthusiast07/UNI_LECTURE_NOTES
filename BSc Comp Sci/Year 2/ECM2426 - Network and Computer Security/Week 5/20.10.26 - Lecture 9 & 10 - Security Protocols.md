
#### NSPK
Needham and Schroeder proposed **NSPK** in 1978 in an attempt to ensure two subjects (users) can communicate authentically - know that they are communicating with the person who they say they are.

**General Idea**
Given two subjects, Alice and Bob, Alice first sends a message to Bob saying she is Alice and her nonce ($N_{A}$), which I encrypted using Bob's public key.
Bob then sends a message back to Alice including her nonce ($N_{A}$) and Bob's own nonce ($N_{A}$), encrypted using Alice's public key.
Alice finally replies with just Bob's nonce, encrypted using Bob's public key.

Firstly, a **nonce**, short for *n*umber used *once*, is a *fresh (secret/random) number* that is *generated at the start of the communication* and is *only known by the subject* (user/principle) who generated it. When it is returned, it is used to show the message is freshly generated; i.e., not an old message.

Finally, public key cryptography ensures the data cannot be read by an unauthorised subject, but it does not ensure that you are communicating with the person who they say they are; i.e., it doesn't provide authenticity. This is why we use NSPK, it ensures you are speaking to the person you think you are.

**Why does it work?**
Alice's nonce ($N_{A}$) can only be read by someone who has Bob's private key; i.e. Bob. When Alice receives a message from Bob, containing $N_{A}$ and $N_{B}$, only she can decode it using her private key. If the nonce ($N_{A}$) sent back matches her's, she knows that she is communicating with Bob, as Bob is the only subject who can read it. Then, once Bob receives the final message from Alice, containing $N_{B}$, if the received $N_{B}$ matches Bob's nonce, then Bob knows he is communicating with Alice, as she is the only subject who can decrypt the message.


#### Security Protocols
A **protocol** contains a set of rules that determines the exchange of messages between two or more subjects.

**Security**, or cryptographic, **protocols** use cryptographic mechanisms to achieve security objectives. Such objectives include subject/message authentication (you are who you say you are), key establishment (secure exchange of encryption keys), integrity (ensuring the message wasn't tampered with during transmission), timeliness, fair exchange, and non-repudiation.


#### Designing a Key Establishment Protocol
The slides walk you through 5 versions of a key establishment protocol that they build up from scratch. They end up with the following specification for this security protocol:

Given two users, Alice (A) and Bob (B), who wish to communicate securely using a session key provided by a central server (S), either user can initiate the protocol, in this example, Bob (B) initiates.
1. B first sends A his nonce ($N_{B}$) along with the fact that he is B - $B \rightarrow A: (B, N_{B})$.
2. A then combines this with her nonce ($N_{A}$) and sends the session key request to the central server S - $A \rightarrow S: (A, N_{A}, B, N_{B})$.
3. S then creates a new session key for users A and B. This is then packages up with the name of the other user (A or B) in the communication and their nonce, which is all encrypted using a pre-shared long-term key specific to each user ($K_{SA}$ or $K_{SB}$) - $S \rightarrow A: (\{|K_{AB},B,N_{A}|\}_{K_{SA}}, \{|K_{AB},A,N_{B}|\}_{K_{SB}})$.
4. Finally, A then forwards B's session key $K_{AB}$ along with his nonce $N_{B}$ to him - $A \rightarrow B: (\{|K_{AB},A,N_{B}|\}_{K_{SB}})$.

Using nonces, we ensure the session keys provided by the server S are fresh and not reused. Also, using a pre-shared key between the server and user ensure the server S is the one who generated the session key.


#### Notation used in Protocol Modelling
**For messages:**
Roles: A, B or Alice, Bob
Agents: a, b
Symmetric Keys: $K_{AB}, K_{SA}, K_{SB}$
Symmetric Encryption: $\{|M|\}_{K}$ - symmetrically encrypt message $M$ using key $K$
Public Keys: $K, pk(A)$ - A's public key
Private Keys: $inv(K), inv(pk(A))$ - inverse of A's public key
Asymmetric Encryption: $\{M\}_{K}$ - absence of $||$ means asymmetric
Signing: $\{M\}_{inv(K)}$ - similar to asymmetric encryption but private key is used
Nonces: $N_{A}$ - A's nonce (number used once)
Timestamps: $T$ denotes time
Message concatenation: $M_{1}, M_{2}, M_{3}$ - commas are used to concatenate messages together

**For communication:**
$A \longrightarrow B: \{A, T_{1}, K_{AB}\}_{pk(B)}$
The long arrow denotes *asynchronous communication* between principles; A and B denote roles. "$A \longrightarrow B:$" is not part of the message.

**For protocols:**
The specification for a protocol includes lots of things; one such component is message sequences, which look identical to the notation used for asynchronous communication, as described above.
