
#### ER Model Properties - Constraints
We covered what an entity, relationship and attribute are in the last lecture, so the last property to cover is constraints, specifically multiplicity.

**Constraints** is a general term used to describe rules that the DBMS and SQL enforce to ensure data integrity (ensuring that all copies are up-to-date/consistent).

**Multiplicity**
**Multiplicity** is one form of constraint which *specifies* the minimum and maximum *number of instances allowed in a relationship between entities*.

Regarding binary relationships; relationships that are between two entity types, there are 3 multiplicity variants: one-to-one, many-to-one/one-to-many, and many-to-many.

**One-to-one**
This constraint says that at most 1 entity type can relate to at most 1 other entity type.
Below are the specific notations used:
 - `0..1` - `0` or `1` instance
 - `1..1` or `1` - exactly `1` instance

**Many-to-one/One-to-many**
This variant says that one instance relates to any number of instances of the other entity and visa versa. We use a `*` to denote many.

**Many-to-many**
This final variant means any number of instances can relate to any number of instances of the other entity type.

You can manipulate the notation to add more precise ranges, for example:
 - `3..7` - means between 3 and 7 instances exactly
 - `1,5,10-12` - means exactly 1 or 5, or between 10 and 12 instances


#### Multiplicity of Complex Relationships
With relationships of more than 2 entities, determining the multiplicity gets more complicated. Therefore, the easiest way is to fix the values of all other entities, then determine the multiplicity of the entity you are interested in; then, repeat this for all entities.


#### Cardinality and Participation
**Cardinality**
The **cardinality** of a relationship is the *maximum* values in each *multiplicity range* on the relationship. It can take the values one-to-one, many-to-one/one-to-many, or many-to-many.

For the above example, the cardinality of the Advertises relationship is *many-to-many*, as this `*` means the maximum is infinite, or more simply "many".

**Participation**
The **participation** of an entity on a relationship is the *minimum multiplicity factor* in the relationship. It takes the values *optional* for `0` and *mandatory* for `1` to `*`.

>[!TIP] The participation of an entity appears on the opposite side of the relationship.


#### Relationship Traps
**Fan Trap**
A **fan trap** exists when two or more *one-to-many relationships fan out from the same entity*, which causes ambiguities with the relationships between the other entities. It makes more sense with the example below:
![[Pasted image 20261007160026.png|498]]
In the above example, the two one-to-many relationship fans out from the `Division` entity. This means that there is no way of knowing which `Staff` members work at which `Branch`. You might think that you can simply add another attribute to the `Staff` entity such as the `branchID` to denote which `Branch` the `Staff` member works at. However, the essence of using the `Branch` primary key in the `Staff` entity creates a relationship.
So, you can solve this in two ways, one is to simply create a new relationship between the `Staff` and `Branch` entities, as described above, but that adds another relationship and more complexity. Therefore, the desirable solution would be to move the entities and their relationships around. Specifically:

This way, you know which `Staff` members work at which `Branch` as well as which `Division` they are in, solving the fan trap.
The fan trap can be summarised as the scenario where a path between certain entities is ambiguous.

A **chasm trap** occurs when there *exists one or more optional participation relationships*. The below example illustrates the chasm trap:

A chasm trap can be summarised as the scenario where a pathway (relationship) doesn't exist between certain entities.


#### Conceptual Database Design Steps
1. Identify entity types
	- For a school, you would have school, student, teacher, etc.
2. Identify Relationships
	- I.e. 1 teacher can teach many classes, and 1 class can have many students.
3. Identify Entity and Relationship Attributes
	- I.e. the name of a student.
4. Determine Primary Keys for Entities
	- I.e. student id
5. Identify Multiplicity Constraints
6. Consider the use of Enhanced Modelling (Optional)
7. Check Model or Redundant Data and any Traps
8. Validate Conceptual Model against User Transactions (Test Queries)
9. Review the Model with the User
