
#### Database Design Hierarchy
**Conceptual Design**
This is what we have been covering in the last 3 lectures; we covered the Entity-Relationship Model as one way of conceptually designing a database. We will know how to convert an ER model to a Relational model next lecture.

**Logical Design**
Today, we cover the logical design; specifically the *relational model*. Confusing name as it is extremely similar to the ER model.

**Physical Design**
The physical design of a database will be covered in future lectures.


#### Relational Model
A **relation** is a *table that represents an entity* from an entity-relationship diagram that *must adhere to certain properties*; hence, some tables are not relations.
****
An **attribute** is exactly the same as with an ER diagram; a *property* of an entity or relation, such as a students name or age.

A **tuple** is a *row in the relation* (table); also called a record.

The **degree** of a relation is the *number of attributes* it has.

Then, the **cardinality** of a relation is the *number of tuples* or rows it has.
****

Relation Properties:
 - Relation's name must be unique
 - Each cell must be atomic - contains only a single value; `forename` and `surname` instead of just `name`, for example.
 - Attributes have a distinct name
 - All the values of an attribute come from the same domain
 - Each tuple/row/record is unique, no duplicates.
 - The order of attributes or tuples has no significance.


#### Relational Keys
These are the same idea as with keys in the entity-relationship model.

A **candidate key** is the *set of all attributes* that can be *used to uniquely identify each tuple* (record) in the relation.

The **primary key** is the *chosen attribute from the set of candidate keys*.

The **alternate keys** are all other candidate keys that were not chosen to be the primary key.

The **foreign key** is the *primary key from another relation or entity* that is used to mark the relationship between the two relations/entities. They are the relational model's form of the relationship lines in an entity-relationship diagram; hence, the ER model doesn't contain any foreign keys.


#### Relational Scheme vs Instance
A **relational schema** is the *definition* of a relation including its name and attributes. Below is an example of a relational schema:

#### Integrity Constraints
**Integrity constraints** are *restrictions* placed on the *values* of particular *attributes*.

**Entity Integrity**
Uniqueness - No two tuples can have identical values for the candidate keys - goes against definition of what a candidate key is.
Not-null - All candidate keys must not contain a null value.

**Referential Integrity**
If a foreign key exists in a relation, either the value matches a primary key value in its home relation or the value is null.

**Domain Constraints**
The set of allowable values for one or more attributes. They enable the Relational DBMS to perform error checks on the data and to determine the range of operations that can be performed on this particular attribute.


#### Data Definition Language (DDL)
All integrity constraints are enforced using the **Data Definition Language (DDL)** which is part of SQL; taught in a couple weeks. 

Below is an example command asking SQL and the DBMS to create a new table (relation); DDL and SQL are designed to be understood by non technical people, so it should be intuitive to understand:
```SQL
CREATE TABLE products (
	productId INT PRIMARY KEY,
	productName VARCHAR(100) NOT NULL,
	categoryId INT,
	CONSTRAINT fk_category
	FOREIGN KEY (categoryId) REFERENCES categories(categoryId)
);
```

You might wonder why we don't explicitly specify `NOT NULL` for the primary key; that is because SQL and the DBMS implicitly insert `NOT NULL`, as that is part of the definition of what a primary key is.


#### Views
A **View** is the *output of a pre-written SQL query*; hence, views are *virtual* - they aren't actually stored in the database, but can be rendered upon request.

Since views are not static copies of a subset of the database; they can *update automatically* simply by "refreshing" or recalculating the view (performing the pre-written SQL query again).

By having pre-written SQL queries, we *enforce security* by not allowing certain users free rein over the database - only letting them see certain relations and attributes; hence, they are *customised to a user's need*.
