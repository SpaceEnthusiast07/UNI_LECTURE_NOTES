
#### Physical DB Design vs. DB Implementation
**Physical DB Design**
The PDBD is the description of how the database is going to be stored on secondary storage.
It includes:
 - Base relations
 - File organisations - how to store the data/ what format
 - Which indexes to use to meaningfully improve the efficiency of the DB
 - What constraints and security measures are you putting in place to ensure data integrity and protection.

**DB Implementation**
The DB implementation stage is the last stage in the DB design process. It is the stage where you take action upon your physical DB design.
Steps include:
 - Using DDL to create the database and the relevant schemas
 - Using DML to populate and update the DB 
 - Develop the applications used by users to interact with the DB


#### Physical DB Design
Obviously, you must know which DBMS you are going to use, have a logical database design (in at least 3rd normal form), and have a set of transactions to be able to physically design the DB.

The steps involved are:
1. Translate the logical data model to be compatible with the chosen DBMS.
2. Design file formats and indexes
3. Design user views
4. Design security measures
5. Consider controlled redundancy
6. Monitor and tune the system

In this lecture we only go through steps 1, 2 and 5.


#### 1. Translating the Logical Data Model
In step 1 you have the following sub steps:

**1.1 Design Base Relations**
In this step we finalise the names of relations (tables) and attributes (columns), and define the data types and lengths of each attribute, how to handle null and default values, and the finalisation of primary and foreign keys, which may introduce surrogate keys - a single attribute taking the place of a composite key. Finally, define how referential integrity is handled; i.e., what happens when a tuple is deleted that is referenced by other tuples.

**1.2 Derived Attributes**
In this step you determine whether you are going to store a derived attribute or calculate it each time it is queried. You may choose to store the attribute if the computation cost is high and the cost of writing it to storage is low. However, you may compute it every time it is queried if it isn't queried frequently, its computational cost is low, or the cost to write the data is high.
Regarding calculation, you can either calculate the value in the `SELECT` section or create a view for reusability. Then, regarding storage, you can either maintain the result with triggers (stored programs that are automatically called when a specific event happens such as inserting, updating, or deleting data), or define a generated column for calculations using a single row.

**1.3 Enforce constraints**
You can enforce certain constraints on data being inserted into the table by using `CHECK` - e.g. `CHECK (Loc IN ('New York', 'Boston', 'Chicago'))`, functions to check other tables, or triggers which are called upon data addition, modification, or deletion.
